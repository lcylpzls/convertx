## 1. 项目背景

### 1.1 行业现状

Go 生态中类型转换相关库呈碎片化分布，尚无单一库同时覆盖"基础类型 + 结构体 + 集合 + 时间"全场景，并内置统一错误封装与数据校验能力。主流竞品各有侧重但均存在明显短板：

| 竞品库 | Stars（约） | 核心能力 | 主要短板 |
|--------|------------|---------|---------|
| `spf13/cast` | ~3.9k | 基础类型互转、时间解析 | 仅支持基础类型；无结构体转换；无校验；错误为原生 `error` |
| `mitchellh/mapstructure` | ~7k+ | map ↔ struct 解码 | 仅 map-struct 双向；弱类型转换有限；slice 异类型转换存在已知 bug；无校验 |
| `jinzhu/copier` | ~3.5k | struct → struct 字段复制 | 错误处理弱；不支持基础类型转换；无校验；tag 体系私有 |

### 1.2 痛点分析

1. **多库拼装成本高**：项目中通常同时引入 `cast`（基础类型）+ `mapstructure`（结构体）+ `validator`（校验），API 风格不统一、错误类型不一致、依赖链冗长。
2. **错误处理不规范**：`cast` 提供 `ToXxx()`（吞错误返零值）和 `ToXxxE()`（返 error）两套，开发者易误用吞错版本；`mapstructure` 错误信息定位困难。
3. **转换与校验割裂**：转换后需手动调用校验库，缺少"转换即校验"的一体化语义，样板代码重复。
4. **指针与嵌套处理繁琐**：现有库对 `*int`、`**struct`、嵌套结构体指针的处理要么不支持，要么需额外配置。
5. **家族生态缺失**：内部已有 `errx`（错误封装）、`validx`（校验）家族库，缺少与之配套的类型转换库，无法形成工具链闭环。

### 1.3 项目定位

`convertx` 定位为 **Go 语言通用类型转换与校验一体化基础库**，对内服务家族生态，对外以 MIT 协议开源。核心设计原则：**统一错误封装、转换校验一体、全场景覆盖、零 panic、零吞错**。

## 2. 业务价值

### 2.1 对内价值

- **统一技术栈**：与 `errx`、`validx` 形成家族工具链，减少项目中第三方转换库的碎片化引入。
- **降低误用率**：强制 `error` 返回 + `errx` 封装，从 API 层面杜绝吞错和 panic。
- **提升开发效率**：转换+校验一体化 API，减少样板代码，统一团队编码风格。

### 2.2 对外价值

- **填补生态空白**：Go 社区缺少同时覆盖基础类型、结构体、集合、时间且内置校验的一体化库。
- **家族品牌建设**：以 `convertx` 为入口，带动 `errx`、`validx` 的社区认知，形成 `x` 系列工具品牌。
- **MIT 协议友好**：宽松许可证降低企业接入门槛，便于社区贡献和生态扩展。

## 3. 核心目标

### 3.1 V1 版本目标（易用性优先）

| 编号 | 目标 | 说明 |
|------|------|------|
| G1 | 基础类型互转 | string / int(8,16,32,64) / uint(8,16,32,64) / float(32,64) / bool / byte / rune 全量互转 |
| G2 | 结构体转换 | struct ↔ struct、struct ↔ map[string]any，支持同名字段、tag 映射、嵌套结构体 |
| G3 | 集合类型转换 | slice ↔ slice（异元素类型）、map ↔ map（异 key/value 类型）、slice ↔ map 互转 |
| G4 | 时间类型转换 | string ↔ time.Time、string ↔ time.Duration、int(timestamp) ↔ time.Time，支持多格式自动识别；支持 UTC 与本地时区互转（`time.Time` 时区转换、string 带/不带时区解析、timestamp 秒/毫秒/微秒/纳秒精度识别） |
| G5 | 指针处理 | 任意层级指针解引用与重建（`*int`、`**struct` 等），nil 安全 |
| G6 | 默认值机制 | 转换失败或源为零值时，支持返回调用方指定的默认值 |
| G7 | 自定义转换函数 | 注册 `func(Src) (Dst, error)` 类型的自定义转换器，支持覆盖内置转换 |
| G8 | 转换后自动校验 | 基于 `validx`，转换成功后自动执行校验规则，失败返回 `errx` 封装错误 |
| G9 | 独立校验快捷 API | 提供基于 `validx` 的校验快捷函数，与转换 API 并列 |
| G10 | 统一错误封装 | 所有错误均通过 `github.com/lcylpzls/errx` 封装，携带转换上下文（源类型、目标类型、字段路径） |

### 3.2 V2 版本目标（高性能增强，向下兼容）

| 编号 | 目标 | 说明 |
|------|------|------|
| G11 | 零反射高性能路径 | 针对基础类型和常见结构体模式，提供代码生成或类型断言的快速路径，性能对标手写转换 |
| G12 | 并发安全缓存 | 结构体元信息（字段映射、转换器链）并发安全缓存，避免重复反射 |
| G13 | V1 API 完全兼容 | V2 新增高性能 API，V1 原有 API 行为不变，平滑升级 |

## 4. 非目标（明确不做）

以下功能 **不在本项目范围内**，杜绝需求蔓延：

| 编号 | 非目标 | 说明 |
|------|--------|------|
| N1 | 不做 ORM / 数据库映射 | 不涉及数据库连接、SQL 生成、表结构映射，仅做内存中类型转换 |
| N2 | 不做完整序列化框架 | 不替代 `encoding/json`、`encoding/xml`、`yaml.v3` 等序列化库；本库处理的是已解析为 Go 值后的类型转换 |
| N3 | 不做深拷贝 | 结构体转换为字段值复制语义，不提供递归深拷贝独立 API |
| N4 | 不做表达式引擎 | 不支持 JMESPath、jq 等路径表达式查询，仅做直接类型转换 |
| N5 | 不做代码生成工具独立交付 | V2 的高性能路径若采用代码生成，作为库内部机制，不交付独立 CLI 工具（V2 阶段再评估） |
| N6 | 不做跨语言绑定 | 仅面向 Go 语言，不提供 CGO、FFI、其他语言绑定 |

## 5. 适用范围

### 5.1 适用场景

- 配置文件解析后的值类型转换与校验（YAML/JSON 解析为 `map[string]any` 后转强类型 struct）
- API 请求参数的类型转换与校验（`string` 入参转 `int`/`time.Time` 并校验范围）
- 领域模型与 DTO 之间的结构体转换（DO ↔ DTO ↔ VO）
- 数据库查询结果（`sql.NullString` 等）与业务模型之间的转换
- 通用工具函数中需要安全类型断言的场景

### 5.2 不适用场景

- 需要 JSON/XML 序列化/反序列化本身（使用标准库或专用序列化库）
- 需要数据库 ORM 映射（使用 GORM、sqlx 等）
- 需要复杂数据查询和转换管道（使用 JMESPath、expr 等）

## 6. 技术约束

### 6.1 语言与运行时

| 约束项 | 要求 |
|--------|------|
| Go 版本 | ≥ 1.26.5 |
| 操作系统 | 跨平台（Linux / macOS / Windows），CI 覆盖三大平台 |
| 架构 | amd64 / arm64 |

### 6.2 依赖约束

**运行时依赖（require）**：

| 库 | 模块路径 | 用途 |
|----|---------|------|
| errx | `github.com/lcylpzls/errx` | 统一错误封装，所有转换失败均返回 `errx.Error`，携带源类型、目标类型、字段路径上下文 |
| validx | `github.com/lcylpzls/validx` | 校验引擎，支撑转换后自动校验（G8）和独立校验快捷 API（G9） |

**测试依赖（require，仅 `_test.go` 引用）**：

| 库 | 模块路径 | 用途 |
|----|---------|------|
| testx | `github.com/lcylpzls/testx` | 简洁断言（Equal/NoError/ErrorIs）、errx 错误码/Kind/字段断言（ErrCode/ErrKind/ErrFields）、表驱动测试、并发测试辅助 |

**依赖约束**：

| 约束项 | 要求 |
|--------|------|
| 第三方依赖 | 仅限家族库（errx、validx、testx）和 Go 标准库 |
| 禁止引入 | 任何非家族的第三方库（如 `spf13/cast`、`mapstructure`、`copier`、`testify` 等） |
| 明确不引入 | `logx`（基础库不直接打日志）、`metricsx`（V1 不内置指标采集，V2 评估可选接入）、其余 21 个家族库（与类型转换场景无关） |
| 家族库版本 | 在 `go.mod` 中锁定具体版本，errx ≥ v1.5.7、validx ≥ v1.2.5、testx ≥ v1.4.5 |

### 6.3 编码约束

| 约束项 | 要求 |
|--------|------|
| 禁止 panic | 所有导出函数不得以任何路径 panic（包括类型断言失败、空指针解引用） |
| 禁止吞 error | 不提供"返零值不返 error"的 API 变体；转换失败必须返回 `errx` 封装的错误 |
| 错误封装 | 所有错误通过 `errx` 封装，携带 `source_type`、`target_type`、`field_path` 上下文 |
| 并发安全 | 导出 API 无共享可变状态；内部缓存需并发安全 |
| 泛型使用 | 充分利用 Go 1.26+ 泛型特性，提供类型安全的泛型 API（如 `convertx.To[int](v)`） |
| 代码风格 | 遵循 `gofmt` + `goimports`，通过 `golangci-lint` 检查 |

### 6.4 测试约束

- 单元测试覆盖率 ≥ 100%
- 每个转换函数必须包含：正常用例、边界用例、异常用例、nil/零值用例
- 结构体转换必须包含：同名字段、tag 映射、嵌套、指针、异类型字段、未匹配字段等场景
- 基准测试（Benchmark）覆盖核心转换路径，作为 V2 性能优化的基线
- 单元测试统一使用 `testx` 断言库，禁止使用 `testify` 或原生 `if err != nil { t.Fatal }` 样板写法

## 7. 风险点

| 编号 | 风险 | 影响 | 应对策略 |
|------|------|------|---------|
| R1 | 反射性能不足 | V1 结构体转换在高频场景（如每秒十万次 DTO 转换）可能成为瓶颈 | V1 明确标注易用性优先；V2 引入零反射快速路径；提供 Benchmark 数据供用户选型 |
| R2 | 泛型 API 与反射 API 设计冲突 | 泛型函数编译期类型确定，反射函数运行时类型确定，两套 API 可能语义不一致 | 统一以泛型 API 为表层，内部复用反射核心；文档明确两种入口的适用场景 |
| R3 | `validx` 家族库依赖不稳定 | 若 `validx` API 变更，convertx 校验功能受影响 | 在 `go.mod` 中锁定 `validx` 具体版本；建立家族库联合 CI，版本升级同步验证 |
| R4 | 结构体转换边界场景遗漏 | 嵌套指针、接口字段、匿名字段、循环引用等场景复杂，易遗漏 | 参考 `mapstructure`、`copier` 的 issue 列表建立边界用例清单；测试覆盖率门禁 ≥ 90% |
| R5 | 自定义转换器注册的全局状态并发安全 | 全局转换器注册表在 init 阶段注册、运行时只读，风险可控 | 注册表使用 `sync.RWMutex` 或 `sync.Map`；文档明确"仅在 init 阶段注册"约定 |
| R6 | 开源社区期望与内部需求冲突 | 开源后社区可能要求加入序列化、ORM 等非目标功能 | 立项书明确非目标清单；Issue 模板中引导用户确认是否在范围内；维护者严格把关 |
| R7 | Go 1.26.5 版本较新，部分用户环境未升级 | 要求 ≥ 1.26.5 可能限制部分用户接入 | 在 README 明确版本要求；评估是否可降级到 1.21+（泛型稳定版），作为 V1.1 优化项 |
